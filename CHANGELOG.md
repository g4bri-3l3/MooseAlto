# Changelog

All notable changes to MooseAlto are documented in this file.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project uses [Semantic Versioning](https://semver.org/).

## [Unreleased]

## [4.0] - 2026-10-07
### Added
- Cloud firewall rules: -InputConfig reads the JSON the vendor CLIs print for Azure Network Security Groups (`az network nsg list -o json`, also ARM REST / Resource Graph), AWS EC2 security groups (`aws ec2 describe-security-groups`) and Google Cloud VPC firewall rules (`gcloud compute firewall-rules list --format=json`, also the Compute REST answer), and runs them through the existing checks. The platform is detected from the content; nothing calls a cloud API. Each rule has a protected side (zone = NSG, group or network name, so -CriticalZones takes those names) and a remote side compared by address, so `0.0.0.0/0` on port 22 covers `10.0.0.0/16` on port 22. Azure rules are ordered by priority with the six default rules at the end, AWS rules are allow-only with no order, GCP rules are ordered by priority (deny first on a tie) with the implied deny-ingress / allow-egress rules added. The Azure `Internet` tag is modeled as the public address space (not RFC1918) rather than any, so `AllowInternetOutBound` doesn't make `DenyAllOutBound` look dead; `AzureCloud` and public IPv6 ranges count as internet; application security groups, referenced groups, prefix lists, GCP tags and service accounts are compared by name. GCP logging and disabled state are read. Normalization notes cover unattached NSGs, source port restrictions, prefix lists, and GCP FQDN / geolocation / threat intelligence sources. New examples `azure_nsg_demo.json`, `aws_sg_demo.json`, `gcp_firewall_demo.json` (from `tools/New-CloudSamples.ps1`) and `tests/Test-CloudImport.ps1`. First release of the cloud importers: tested on those generated demos and on the sample outputs of the official AWS and Azure documentation, not yet on exports from live environments, and not on any Google Cloud vendor sample.

### Changed
- Azure: the six default rules of each NSG (`AllowVnetInBound`, `DenyAllInBound`, ...) stay in the model, so custom rules are still compared with them, but no finding is reported on them since they can't be changed. They are still listed in the Internet Exposure Inventory.
- On cloud rules only: `port_based_rule_missing_app_id`, `no_security_profile_on_exposed_rule` and `negated_rfc1918_effectively_public` don't run (cloud rules match ports only, take no inspection profile and can't negate), an Internet-wide destination isn't reported as a "defined destination" (`outbound_defined_dest_any_app`), and a logged deny-all is recognized as the cleanup rule without zones of any. Findings for PAN-OS, FortiGate, SRX and Tufin inputs are unchanged.

### Fixed
- PAN-OS `drop` and `reset-client` / `reset-server` / `reset-both` actions were not treated as deny: `allow_shadows_deny` and `deny_shadows_allow` missed them (FortiGate, SRX and Tufin inputs already mapped them to deny), and `rule_name_action_mismatch`, the intrazone check and the cleanup rule check ignored the reset actions.
- `allow_shadows_deny` / `deny_shadows_allow` blamed a later rule when an earlier rule with the same action already covered the one being checked (a deny already dropped by an earlier deny was reported as "permitted" by an allow further down). Only the first covering rule counts now.
- PAN-OS CSV: a row with fewer fields than the header, with a `Disabled` column present, was dropped with an error; it is analyzed now, and truncated rows and rules with an empty Action are reported on the console. Tufin rows with an empty Action cell get a normalization note.
- Name based checks (`generic_rule_name`, `rule_name_action_mismatch`, temporary keywords) did not work behind the `<device>/` (Tufin), `<vdom>/` (FortiGate) and logical system prefixes, or on a PAN-OS rule renamed with `(duplicate name #N)`.
- Tufin: a device name containing `/` was cut at the slash when deciding which devices collect hit data, so two devices could be mixed up.
- SRX: `any-ipv6` next to IPv4 addresses turned the side into any; excluding `any` (`source-address any` with `source-address-excluded`) was read as any instead of a policy that can never match; a zone name used by two logical systems shared one internet / intrazone hint.
- `missing_explicit_intrazone_internet_deny` and `no_explicit_deny_log_rule` are checked per device, VDOM or logical system: a cleanup rule on one device no longer hides the gap on another.
- The "Deny / drop" card of the report statistics did not count `reset-*` rules.
- PAN-OS address group members are split on `,` as well as `;`, like every other multi-value field.
- `tools/ConvertTo-*Config.ps1` found Hit Count / Last Hit / Rule Usage only under their exact short names, so round trips of a real PAN-OS 12 export ("Rule Usage Hit Count") lost all usage data.
- tests: `Test-ParserFixes.ps1` covers each fix above.

## [3.0] - 2026-09-28
### Added
- Interactive setup: Tab completion of file and folder names in every path question (input file, output paths, hit counter file, object CSVs, comparison CSV, saved report).
- Tufin SecureTrack Rule Viewer CSV export (R25-2 columns): one file with many devices and vendors, one report. Rules are named `<device>/<rule>`, compared only within their device and policy, and worded per vendor; zoneless rules (Check Point) are judged on their addresses; `Last Hit` drives the usage checks (empty = no hits on a device that has hit data). Object and group names are compared by name, not resolved (Known limitations). A missing required column stops the import with the columns to add; a missing optional one is reported and its checks are skipped, never run on empty values. `examples/tufin_rule_viewer_sample.csv` and `tests/Test-TufinImport.ps1`.
- `-NoSecurityProfileChecks` (also a setup question): for a firewall that does no IPS / antivirus / URL filtering because another device does it. `no_security_profile_on_exposed_rule` is not run, Gemini is told not to recommend security profiles, the report states the check was off, and the setting is kept in the run context for a later saved-report analysis.
- FortiGate input: `-InputConfig` reads a FortiOS 6.x or 7.x configuration (backup file or `show full-configuration`), single or multi VDOM, profile-based or NGFW policy-based mode, and runs it through every existing check. Objects, nested groups, VIPs (resolved to the mapped internal address, the host a policy actually exposes), predefined and custom services, service groups, negation, Internet Service destinations, profiles, logging, comments, zone intrazone settings and disabled state are all mapped; the full table is in the README.
- FortiGate application control: FortiGuard application IDs in NGFW security policies are translated to the names the risky application checks use (15511 becomes `ms-rdp`), and `enforce-default-app-port` with no service becomes `application-default`, so application based checks work on FortiGate exactly as on PAN-OS. IDs are resolved from the configuration's own `config application name` table first, then from `-AppMapCsv`, then from a built-in table (19 IDs verified individually on FortiGuard, the rest from a public ID table that agrees with every verified one).
- Juniper SRX input: `-InputConfig` also reads a Junos configuration, as `show configuration | display set` or in hierarchical form, root and logical systems. Zone pair and global policies (in SRX evaluation order), global and zone attached address books, address-sets, `junos-*` predefined and custom applications, application-sets, AppSecure `dynamic-application` (with `junos-defaults` mapped to `application-default`), excluded addresses, application services as profiles, `log session-init/session-close` as logging, descriptions, `deactivate` and `inactive:`, and `default-policy permit-all` (turned into an explicit trailing allow rule) are all mapped.
- `-HitCountFile` (alias `-UsageJson`): per rule usage data in the form each platform exports it, also asked by the interactive setup. PAN-OS: a rule usage CSV (Policy Optimizer export) whose Hit Count / Last Hit / Rule Usage replace the rules CSV values for the rules it lists, matched by name; unmatched rules, orphan names and duplicate names are reported. FortiGate: the monitor API JSON (`firewall/policy` or `firewall/security-policy`), one response or an array across VDOMs. SRX: the text output of `show security policies hit-count`. Missing counters stay unknown, never zero; the console reports coverage, and a file in the wrong format or from the wrong endpoint is reported instead of silently ignored. A missing file stops the run.
- Internet facing zones taken from the configuration and added to the internet zone set, with a console note: FortiGate interfaces with role WAN and SD-WAN zones, SRX zones behind the default route.
- Normalization notes: every conversion that loses information on a specific rule (for example exclude-member groups, dynamic addresses, identity restrictions, port ranges too large to expand, unknown applications, application groups and categories, URL categories, service-negate) is written to `<report>_normalization.txt` next to the HTML report.
- AI analysis of a saved report: `-AnalyzeFindingsCsv <findings.csv>`, also option 2 of the start menu (1 setup, 2 saved report AI analysis, 3 exit), runs only the Gemini step on a findings CSV from an earlier run, in seconds, without parsing or checking the ruleset again. Meant for large rulesets, for analysis done offline where the exports live with only the findings moved to a machine that can reach Gemini, and for reviewing or trimming the CSV before sending: removed rows are not sent, and the names of rules removed or renamed in the CSV are masked (RULE-WITHHELD-N) where other findings quote them. Writes only the AI report, `<name>_ai.html`, and only when Gemini returns results (declined, nothing to send or a failed call write nothing): no CSV is created and the input is never modified; `-CompareTo` adds the trend narrative. Same consent questions, IP masking and disabled rule exclusion as a live run.
- Run context file: every run writes `<report>.context.json` next to the findings CSV (ruleset as analyzed, inventory, vendor, settings; local only, never sent), used by the saved-report analysis to rebuild the full report, offer the Tags question and use the vendor's prompt. Reports without it (MooseAlto 2.x) still work from the CSV alone.
- `-ExportNormalized <folder>`: writes an imported configuration as PAN-OS style CSVs, for debugging an import or feeding another tool.
- Importer syntax checked against public references: Fortinet's official Ansible collection (option names and value choices per FortiOS version), a FortiGate monitor API response captured on a production unit (prometheus fortigate_exporter test data), the Batfish Juniper grammar and test configurations, Juniper's unified policy documentation and its application signature pages. Fixes that came out of it: SRX application terms with several attributes on one line (`term t1 protocol tcp destination-port 1`, the form Junos itself prints) were read as protocol only; `any` inside an application-set gave a spurious warning; single level AppSecure groups (`junos:p2p`, `junos:web`) were read as applications; `icmp6-type` was ignored; a match condition chained on one CLI line is read in full; FortiOS 7.x `application group` of `type filter` (criteria such as risk or popularity that a configuration cannot expand) is kept as one opaque token instead of expanding to its category only. The SRX predefined application table now covers the whole junos-defaults group (174 applications, 23 application-sets, from the published `show groups junos-defaults applications` output plus the entries added in later releases); `junos-ping` is corrected to all ICMP (it is `protocol 1`, only `junos-icmp-ping` is echo request) and `junos-smtps` to TCP 587.
- Risky ports and applications verified on every vendor: `tests/fixtures/risky_matrix.csv` holds one inbound and one outbound rule for every entry of the risky port, risky application and amplification lists, and runs as a FortiGate NGFW, FortiGate profile-based and SRX round trip in the regression. Gaps it found and closed: FortiGuard application IDs for Oracle, Rsh, Rlogin, Rexec, GoToMyPC, Chrome Remote Desktop, UPnP/SSDP, NetBIOS Name Service, SMB v1/v2 and Windows File Sharing; FortiOS default services REXEC, RLOGIN, RSH, DCE-RPC, ONC-RPC and the other 7.x defaults, which were read as unknown services and escaped the port checks; SRX AppSecure GoToMyPC and Elasticsearch spellings; custom SRX applications named after a remote access tool (for example `AnyDesk-Custom`) now keep the name, as FortiGate services already did, so the service name check sees them.
- `examples/corner_cases_1000.csv` (from `tools/New-CornerCaseDataset.py`) with its FortiGate and SRX versions: 1,000 rules that trigger 42 of the 43 finding types and their corner cases, in the regression and as round trips on all three vendors.
- tests/: one command regression (`Invoke-Regression.ps1`) covering the AI step with a simulated Gemini response (no key or network needed), a syntax check, reference datasets with exact expected finding counts (`regression.json`, extendable with private datasets), FortiOS and SRX importer assertions on hand written fixtures, and round trips: a PAN-OS CSV converted to an equivalent FortiOS or SRX configuration (tools/) and compared finding by finding against the original, with every known difference kept in a snapshot.

### Changed
- `plain_dns_to_unrestricted_destination` and `plain_dns_to_known_resolver` also fire for the DNS application (`dns`, `dns-base`), not only for port 53: the same traffic written the App-ID way or the port way now gets the same finding, on every vendor.
- Gemini request, no IP address ever: rule names are now masked too (`Allow-10.1.1.1` becomes `Allow-IP-MASKED-1`), as well as IPv6 addresses and IPv4 written with `_` or `-` between the octets (`Host_10_1_1_1`, `net-192-168-10-0`), everywhere text is sent (findings, tags, trend). The same address gets the same placeholder in every form. The final request is checked again with the same patterns right before it leaves: if an address were still in it, nothing is sent. The model's answers about a masked rule name are matched back to the real rule locally.
- Checks whose meaning depends on the platform now adapt to the source vendor. PAN-OS results are unchanged: all example datasets produce byte identical findings and inventory CSVs.
  - `port_based_rule_missing_app_id`: on FortiGate, not reported when an application control profile is applied, and the text recommends application control; on SRX it recommends AppSecure.
  - `missing_explicit_intrazone_internet_deny`: only where intrazone traffic is really allowed without a rule (every zone on PAN-OS; FortiOS zones with `intrazone allow`; on SRX only with `default-policy permit-all`).
  - `rule_usage_unused` / `rule_usage_partially_used`: Panorama verdicts, never derived from hit counts on other vendors (a zero hit count is `zero_hit_count`, so the same fact is not reported twice).
  - Finding texts say "application" instead of "App-ID" for FortiGate and SRX rules.
- Vendor is detected from file content: a configuration passed to `-InputCsv`, including through the interactive setup, is analyzed as a configuration instead of failing as a malformed CSV.
- A hit counter or rule usage file given as the file to analyze (FortiGate monitor API JSON, SRX hit-count output, PAN-OS rule usage CSV) is recognised and explained: the interactive setup keeps it as the hit counter file and asks for the configuration, the command line stops with the right usage. A file in no known format is refused instead of being read as a PAN-OS CSV (a `.csv` file is still read as one, as before). Quotes around a path pasted in the interactive setup are accepted.
- Interactive setup follows the input type: address object/group files and a rule usage file for a PAN-OS CSV, hit counter file and application name map for FortiGate and SRX. The review list is rebuilt when the input file changes.
- Report title and the Gemini system prompt follow the source vendor, so AI remediation advice uses FortiOS or Junos features rather than PAN-OS ones.
- Banner tagline reads "Firewall Rule Analyzer".
- After the AI step of a live run, that run's findings CSV is rewritten with Suggested Fix and MITRE ATT&CK columns (previously only the HTML and JSON had them). Offline CSVs are unchanged.
- The question about including rule Tags in the Gemini prompt is skipped when no rule has Tags.
- The AI step is a function shared by live runs and saved-report analysis; its behavior in a live run is unchanged.

### Fixed
- `generalization_anomaly` could pair a rule with a broader rule of another VDOM or logical system; it is now limited to the same scope, like the other pairwise checks.
- Shadowing, duplicate and anomaly checks compared rules of different FortiGate VDOMs or SRX logical systems with each other (the same policy in two VDOMs was reported as a duplicate). They are now compared only within the same scope; PAN-OS output is unchanged.
- Address objects and groups (checked across the three vendors with `examples/objects_corner_*.csv` and `rules_5000_with_objects.csv` round trips, plus `tests/Test-AddressResolution.ps1`):
  - A FortiGate `interface-subnet` object without a subnet line resolved to 0.0.0.0/0 (any); it now takes the interface's subnet, or stays opaque.
  - IPv6 addresses and bare numbers were read as IPv4 (`2001:db8::1` as 0.0.0.1, inside 0.0.0.0/0; an object named `10` as 0.0.0.10); only dotted IPv4 is an address now, the rest stays opaque. SRX IPv6 addresses get their own type, as on FortiGate.
  - A negated object or group in a PAN-OS CSV (`[Negate] GUEST-G`) stayed one opaque token; it is resolved now, as FortiGate and SRX already did.
  - An empty group resolved to an empty field; it is one opaque token now.
  - `negated_rfc1918_effectively_public` fired when only part of the private space was negated (`[Negate] 10.60.0.0/16` is not "any public"), and `all_rfc1918_effectively_private` fired on 0.0.0.0/0; both now require exactly what their text says. The rules still count as broad for the other checks.
  - Generators (`tools/`): `-AddressObjectsCsv` / `-AddressGroupsCsv` write objects and groups (nested groups in dependency order, ranges, fqdn, wildcard with the mask inverted to the FortiOS / Junos convention), so rules that use them survive the conversion.
- Code review of 3.0 before release (every item reproduced first, then covered by a test):
  - FortiGate: `append` joined values into one string; Internet Service groups, custom groups and `-src-` variants ignored (destination became any); `internet-service-src-negate` ignored; objects with the same name in different VDOMs overwrote each other (now `<vdom>/<name>`); VIPs without `mappedip` (load balance, fqdn) resolved to any; the `none` address read as any; `srcaddr6 all` removed the IPv4 restriction; a negated `all` (matches nothing) read as match everything; a hit counter file with a single policy lost; IPv6 objects read as IPv4; application control inside a profile group not recognised.
  - SRX: deactivating a single leaf disabled the whole policy, while deactivated objects, set members and `default-policy` still counted; address names defined differently in several address books merged (now resolved through the policy's zones); an application-set `description` read as a member; numeric protocols and many named ports (`netbios-ssn`, `sunrpc`, `login`, ...) and named ICMP types not understood; only the last address of an interface kept (internet zone missed); a global policy lost its hit count when a zone pair policy had the same name; a hierarchical config with an annotation starting with "set" read as set format; `apply-groups` not expanded; rule names prefixed with the logical system even when only one had policies; a policy without `then` or without any match (which Junos does not commit) imported as a deny any rule that shadowed everything after it.
  - All vendors: address objects of type ip-range now resolve to their range, like a literal range in the rule, so they get the same containment analysis (on PAN-OS only the displayed text of those rules changes, findings are identical); `generic_rule_name` also recognises underscores (`New_Rule`), since SRX names cannot contain spaces.
  - Gemini request: the IP masker corrupted an address that another one is a prefix of (`10.1.1.1` vs `10.1.1.10/24`); an empty Detail sent the previous finding's text; Tags sent without IP masking; resolved findings in the trend sent without rule name; a withheld rule name containing an IP partly leaked.
  - A usage file with more than 20 columns lost its Hit Count and Last Hit; blank cells in a usage file overwrote the rules CSV values; an empty usage file was silently ignored; zero findings wrote an empty CSV that `-CompareTo` and `-AnalyzeFindingsCsv` then refused; an empty rulebase crashed instead of stopping with an error; the run context never stored the processing time.
  - Interactive setup: option 2 did not accept a quoted path; a blank API key did not skip the AI step. Wording: SRX `default-policy permit-all` got the PAN-OS intrazone text; the AI guess said "App-ID" for FortiGate and SRX; `-ExportNormalized` invented a Panorama Rule Usage column.
  - Generators (`tools/`): port ranges now defined, duplicate names made unique, Disabled and logging carried over from the CSV, SRX names limited to the characters Junos accepts, descriptions quoted, one default route per WAN zone.
- Hit counts above 2,147,483,647 (common on busy edge rules) no longer stop the run: `zero_hit_count` and `stale_last_hit` read the counter as a 64 bit value.

## [2.1] - 2026-09-23
### Added
- generalization_anomaly: an earlier, narrower rule fully covered by a later, broader rule using a different action (the Al-Shaer/Hamed Generalization anomaly, the same term Palo Alto Strata Cloud Manager uses in its Policy Analyzer). The narrow rule still fires today as a deliberate looking exception ahead of the broad one; the risk is fragility, not brokenness. Removing that rule during cleanup, on the wrong assumption the broad rule already covers it, or reordering the two, silently changes the effective behavior for its traffic, with nothing in the firewall itself flagging the change. Low severity: a warning to confirm intent, not a confirmed misconfiguration. Detected through a bounded backward scan, run only when the current rule looks broad enough to plausibly generalize something (wildcard zone, or source/destination address left as any), so the added cost scales with how many such broad rules exist, not with the square of the ruleset size.
- correlation_anomaly: two rules with different actions whose match criteria partially overlap without either one containing the other (the other half of the same Al-Shaer/Hamed pair, called Correlations in Strata Cloud Manager). Neither rule is dead policy and neither is a deliberate exception; for traffic caught in the overlap, the effective action depends only on which rule sits first in the rulebase, something neither rule states on its own. Low severity, reported once per rule.
- exposed_amplification_prone_service: allow rule reachable from the internet on a UDP service known to be abused for reflection and amplification DDoS (NTP, SSDP/UPnP, mDNS, NetBIOS Name Service, Memcached, Chargen, QOTD, full list in README), matched by App-ID or by UDP port through a port parser limited to UDP (the same port number over TCP does not carry this risk, since it needs a spoofable, connectionless response). Framed as a risk to third parties, not only to this network: the attacker spoofs a victim's source address, and a server answering this from the open internet becomes the reflector, sending its, often much larger, response to the victim instead of back to the attacker. High severity. Extensible through the two new optional keys in `-RiskyTaxonomyPath`, `amplificationPronePorts` and `amplificationProneApplications`.
- generic_rule_name: rule named after a generic template rather than what it actually controls (Rule 5, New Rule, Policy #12, a bare number, and similar, matched in both English and Italian). This kind of name only works if the reader also knows the rule order; on its own it says nothing about the traffic. Low severity.
- compliance_tag_without_critical_zone: allow rule tagged with a compliance or critical scope keyword (pci, swift, cde, cscf, hipaa, phi, sox, ffiec, core banking, atm, hsm) whose source and destination zone are both outside the configured `-CriticalZones` set. Either the tag no longer matches what the rule actually touches, or the critical zone list is missing something the organization already considers in scope. Skipped when either zone is any, since any already includes the critical zone among everything else it matches. Medium severity.
- no_explicit_deny_log_rule: ruleset wide check for a broad deny or drop rule (any zone, any address, any application, any service) with logging enabled. Without one, whether traffic caught by the implicit default deny is actually logged depends on a device setting this export cannot see. Low severity, a defense in depth recommendation rather than a confirmed gap; skipped entirely when the export never shows logging information anywhere, same gate as 'no_logging_enabled'.

### Changed
- RiskyTaxonomyPath json schema extended with two more optional top level keys, 'amplificationPronePorts' and 'amplificationProneApplications', merged the same additive way as the existing 'riskyPorts'/'riskyApplications' (a custom entry sharing a key with a built in one only overrides that entry's label).

## [2.0] - 2026-09-11
### Added
- The Findings table (report and CSV export) and the Internet Exposure Inventory now show the resolved IP/CIDR alongside a raw address-object or group name when -AddressObjectsCsv/-AddressGroupsCsv resolution actually changed something (e.g. Network1 (10.0.0.0/8)), so a reader doesn't need to cross-reference the objects file separately to know what a name means. Left as just the name when resolution didn't apply.
- RiskyTaxonomyPath: an optional JSON file extending the built-in risky-port/application tables with environment-specific entries.
- OutJson: a structured JSON Lines export of the findings (one finding per line, each an independently parseable JSON object with metadata repeated on every line) meant for a SIEM or other automated consumer. Chosen over a single nested JSON document specifically because log-oriented ingestion (Splunk and similar) indexes JSON Lines automatically, with fields like severity/rule_name/type immediately searchable, no unpacking required. Written once after the deterministic report and again (overwriting) after the optional Gemini step if that ran, so it reflects Suggested Fix/MITRE tags when available.
- Trend narrative on -CompareTo: when a comparison against a previous report has actual changes, and the optional Gemini step runs, you're asked separately whether to also get a short AI narrative about the trend (what got fixed, what's new, whether it reads as real progress or churn), shown under the New/Resolved/Still-present counts.
- "-Model" now appears in the guided interactive setup and in the review
  and edit console, not just on the command line. Prompt shows the
  current default (gemini 3.7 flash) and accepts a blank answer to keep
  it. Toggling AI analysis back on inside the console also brings the
  Model row back with it.
### Fixed
- Zone="any" no longer implies internet-touching on a ruleset where no zone actually named as an internet zone (via -InternetZones) exists anywhere at all - a purely internal firewall, with no Untrust/external- equivalent interface on the device. Computed once per ruleset (does at least one real zone in use anywhere match a configured internet zone name); when the answer is no, "any" matching "every zone the firewall knows about" can no longer include the internet, because none of those zones IS the internet. A concrete public/negated address is unaffected either way, since that evidence is independent of zone naming. Where a real internet zone does exist somewhere in the ruleset, behavior is unchanged.
- Address-object resolution silently failed for a common variant type spelling: the code matched only the literal string "ip-netmask", so an export using "IP Netmask" never resolved at all, leaving the raw object name as an opaque token for every downstream check that depends on knowing whether an address is public or private. Object types are now normalized (lowercased, spaces collapsed to hyphens) before comparing.
- A large ruleset needing multiple Gemini batches produced a visibly repetitive AI section: each batch's prompt didn't know it was only seeing a slice of the findings, so every batch tended to write a "complete" executive summary describing the same dominant, ruleset-wide issues (e.g. one broad any/any rule whose shadowed-rule findings spread across several batches), and those near-duplicate summaries were then simply concatenated. Fixed on both ends: batches are now told when they're one of several and asked to describe only what's actually in front of them, and the final report uses just the summary from the batch with the most Critical/High findings (noting how many batches ran) rather than stitching every batch's summary together. The remediation list is also deduplicated by shared rule-name tokens across batches, so the same headline rule recommended three or four times in slightly different words collapses to one entry.
- Gemini calls stopped giving up on the very first client side timeout.
  HttpClient's own default timeout (100 seconds) could expire before a
  larger batch got an answer, surfacing as a raw TaskCanceledException
  ("A task was canceled") straight
  out of GetAwaiter().GetResult(). That path used to return immediately
  instead of going through the retry logic already built for transient
  HTTP errors (429/500/502/503/504), so "attempt 1/3" never actually
  reached attempt 2 or 3. The request timeout is now explicit (180
  seconds) and a client side timeout retries with the same exponential
  backoff as those HTTP errors.

## [1.8] - 2026-09-07
### Added
- Port 80 (HTTP) added to the risky-port list, marked cleartext like FTP/Telnet/etc. Previously absent entirely, not just excluded from the cleartext subset.
- MITRE ATT&CK tagging: when the optional Gemini step runs, findings that clearly correspond to a well-known technique get tagged with its ID, name, and tactic in a new column, shown only when at least one finding has been tagged. The model is instructed to skip a finding rather than force a speculative or overly generic tag.
- Interactive setup now ends with a review-and-edit loop once the guided question sequence completes: every parameter is listed with its current value, and typing a number or a parameter name (by either, case-insensitive) lets you change just that one setting and come back to the list, instead of having to restart the whole wizard to fix one answer. Press Enter with no changes to proceed.
- Large rulesets that produce enough findings to risk exceeding Gemini's free-tier input-token quota are now automatically split into multiple smaller batches, sent one after another, with results merged afterward. A console note explains when this kicks in. Batches are spaced more than 60 seconds apart, since the quota that matters is cumulative per minute, not per request. Sending several comfortably-sized batches only a few seconds apart can still trip the same quota this batching exists to avoid.
### Changed
- The Suggested Fix column now only appears when the optional Gemini step actually runs.
### Fixed

## [1.7] - 2026-08-31
### Added
- Suggested Fix column on the Algorithmic-based Findings table, shown whenever at least one finding has one. Filled in automatically (no AI needed) for finding types with an obvious, context-free next step: disabled_rule_present / rule_usage_unused / stale_last_hit (candidates for removal, confirm with the rule owner), duplicate_rule / shadowed_rule (remove, covered by an earlier rule), and temporary_tag_but_broad_rule / temporary_tag_still_present (confirm still needed, remove tag or rule if not). AI guesses are clearly prefixed "AI guess (verify):" and are never applied automatically; a finding is left without one if there's no real hint in the name/ tags/port to go on rather than guessing something generic. Applying a suggestion (deterministic or AI) rebuilds the report from the already-computed findings, no re-detection involved.
- Table columns on the Findings and Inventory tables can now be dragged to a new position by their header label (distinct from the resize handle on the right edge of each header). Moving a column reorders it consistently across the header, the filter row, and every data row, so filtering keeps working correctly regardless of column order. Works with both mouse and touch.
### Fixed
- internet_exposed_any_field no longer counts Application left as "any" as an open dimension when Service is pinned to a specific port (e.g. tcp/8080). That combination is a port-based rule, not a wide-open one, and was already its own finding (port_based_rule_missing_app_id); counting it here too overstated how open the rule actually was. Application still counts normally when Service is also effectively any.
- outbound_defined_dest_any_app had the same issue as the fix above, and is fixed the same way: Application left as "any" only counts as unrestricted when Service is also effectively any, not when Service is pinned to a specific port.
- The same Application/Service issue as the two fixes above was also present in five more places, found by systematically re-checking every spot that looks at whether Application is "any": unrestricted_access_to_critical_zone, unrestricted_egress_from_critical_zone, temporary_tag_but_broad_rule (which was also missing a Service check entirely, not just misapplying one), broad_internal_exposure (which used a plain null check on Service instead of the shared effectively-any helper, missing the application-default-with-no-app edge case too), and missing_explicit_intrazone_internet_deny (the mirror situation: a Deny rule with Application=any but Service pinned to one port doesn't actually block all traffic between the zone and itself, so it shouldn't count as satisfying the "explicit deny" requirement either). All five fixed the same way, reusing the shared Service-effectively-any check.
- Direction classification (Test-SideIsInternet, which most findings key off of) no longer treats a rule as internet-facing purely because its zone is "any" if the address field on that same side is exclusively a specific, plain private IP/CIDR. PAN-OS matches zone and address together on a rule, not either alone, so a rule scoped to zone="any" but a concrete private host (e.g. 10.5.5.10/32) can never actually be reached from internet, no matter how broad the zone field looks by itself. A specifically-named internet zone (e.g. Untrust) is unaffected by this and still counts as before; so does any address that's public, negated, a range, or an unresolved object name, only an unambiguous, exclusively-private plain IP/CIDR overrides the zone="any" signal.
- inbound_risky_application / outbound_risky_application / internal_risky_application now also check the Service field for a risky application name, not just Application. Real, especially older, rulebases sometimes use a custom-named Service object literally named after the protocol instead of, or alongside, App-ID (e.g. a Service named "smtp") - a pre-App-ID naming convention that was previously invisible to these checks entirely, since Service was only ever scanned for port numbers. Also matches a name with a port or other suffix appended to it (e.g. "smtp-25", "SMTP_Relay_25"), by checking each sub-token split the same way rule names are tokenized elsewhere in this file, not just an exact whole-field match.
