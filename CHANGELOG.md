# Changelog

All notable changes to MooseAlto are documented in this file.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project uses [Semantic Versioning](https://semver.org/).

## [3.0] - 2026-10-05
### Added
- FortiGate support: -InputConfig reads a FortiOS 6.x or 7.x configuration (a backup file or the output of `show full-configuration`), single or multi VDOM, profile-based or NGFW policy-based mode, and runs it through every existing check. Objects, nested groups, VIPs, predefined and custom services, service groups, negation, Internet Service destinations, profiles, logging, comments, zone intrazone settings and disabled state are all translated; the full table is in the README. A VIP is read as its mapped internal address, since that's the host the policy actually exposes.
- FortiGate application control: FortiOS stores applications as numeric FortiGuard IDs, so they're translated into the names the risky application checks already use (15511 becomes `ms-rdp`). An ID is looked up in the configuration's own `config application name` table first, then in -AppMapCsv, then in a built-in table (19 IDs checked one by one on FortiGuard, the rest from a public ID table that agrees with every one we checked). A policy with `enforce-default-app-port` and no service is read as `application-default`, exactly like on PAN-OS.
- Juniper SRX support: -InputConfig also reads a Junos configuration, as `show configuration | display set` or in the hierarchical form, root and logical systems. Zone pair and global policies (in the order SRX evaluates them), global and zone attached address books, address-sets, `junos-*` predefined and custom applications, application-sets, AppSecure `dynamic-application`, excluded addresses, application services, session logging, descriptions, deactivated policies and `default-policy permit-all` (added as an explicit allow rule at the end, so the checks see it) are all translated.
- Tufin SecureTrack support: -InputCsv also reads the CSV exported by the SecureTrack Rule Viewer, one file with many devices of different vendors, one report. Rules are named `<device>/<rule>` and only compared with rules of the same device and policy, and the finding text follows each rule's vendor. Rules without zones (Check Point) are judged on their addresses, and the Last Hit column drives the usage checks (an empty cell means no hits, but only on a device where other rules do have a date). Object and group names are compared by name, since the export doesn't say what's inside them (see Known limitations). A missing required column stops the import and tells you what to add; a missing optional one is reported and the checks that need it are skipped, never run on empty values.
- -HitCountFile (alias -UsageJson): per rule usage data, in the form each platform exports it, also asked by the interactive setup. On PAN-OS it's a rule usage CSV (Policy Optimizer export) whose Hit Count / Last Hit / Rule Usage replace the rules CSV values for the rules it lists, matched by name; rules it doesn't list, names that match no rule and names listed twice are reported. On FortiGate it's the monitor API JSON (`firewall/policy` or `firewall/security-policy`), one response or an array across VDOMs. On SRX it's the text output of `show security policies hit-count`. A missing counter stays unknown, never zero. The console tells you how many rules got a counter, and a file in the wrong format, or from the wrong endpoint, is reported instead of being silently ignored. A hit counter file that doesn't exist stops the run.
- Internet facing zones read from the configuration itself and added to the internet zone set, with a console note: FortiGate interfaces with the WAN role and SD-WAN zones, and on SRX the zone behind the default route.
- Normalization notes: whenever translating a FortiGate, SRX or Tufin rule loses information (exclude-member groups, dynamic addresses, user restrictions, port ranges too large to expand, unknown applications, application groups and categories, URL categories, service-negate and so on), it's written to `<report>_normalization.txt` next to the HTML report, so you know which findings to read with more care.
- AI analysis of a saved report: -AnalyzeFindingsCsv <findings.csv>, also option 2 of the start menu, runs only the Gemini step on the findings CSV of an earlier run, in seconds, without parsing or checking the ruleset again. Useful on large rulesets, when the analysis has to run offline where the exports live and only the findings can move to a machine that reaches Gemini, and when you want to review or trim the CSV before sending it: deleted rows aren't sent, and the names of rules removed or renamed in the CSV are masked (RULE-WITHHELD-N) where other findings quote them. It only writes the AI report, `<name>_ai.html`, and only when Gemini actually answers; it never creates a CSV and never touches the input. -CompareTo adds the trend narrative, and the consent questions, IP masking and exclusion of disabled rules are the same as in a live run.
- Run context file: every run writes `<report>.context.json` next to the findings CSV (the ruleset as analyzed, the inventory, the vendor and the settings). It stays local and is never sent anywhere; the saved report analysis uses it to rebuild the full report, ask the Tags question and use the right vendor's prompt. Reports without it (MooseAlto 2.x) still work from the CSV alone.
- -NoSecurityProfileChecks (also a setup question): for a firewall that deliberately does no IPS / antivirus / URL filtering because another device takes care of it. no_security_profile_on_exposed_rule isn't run, Gemini is told not to recommend security profiles, the report says the check was turned off, and the setting is remembered for a later saved report analysis.
- -ExportNormalized <folder>: writes an imported configuration as PAN-OS style CSVs, handy to see exactly what the import produced, or to feed another tool.
- Interactive setup: Tab completion of file and folder names in every question that asks for a path (input file, output paths, hit counter file, object CSVs, comparison CSV, saved report).
- Importer syntax checked against public references: Fortinet's official Ansible collection (option names and values per FortiOS version), a FortiGate monitor API response captured on a production unit, the Batfish Juniper grammar and test configurations, and Juniper's own documentation. A few things came out of it and were fixed: SRX application terms with several attributes on one line (`term t1 protocol tcp destination-port 1`, which is how Junos itself prints them) were read as protocol only; `any` inside an application-set gave a spurious warning; single level AppSecure groups (`junos:p2p`, `junos:web`) were taken for applications; `icmp6-type` was ignored; a match condition chained on one CLI line wasn't read in full; a FortiOS 7.x `application group` of `type filter` (risk, popularity and similar criteria a configuration can't expand) was expanded to its category only, and is now kept as one opaque token. The SRX predefined application table now covers the whole junos-defaults group (174 applications and 23 application-sets); `junos-ping` is corrected to all ICMP (only `junos-icmp-ping` is echo request) and `junos-smtps` to TCP 587.
- Risky ports and applications verified on every vendor, with one inbound and one outbound rule for every entry of the risky port, risky application and amplification lists, written as FortiGate NGFW, FortiGate profile-based and SRX configurations. The gaps this found were closed: FortiGuard IDs for Oracle, Rsh, Rlogin, Rexec, GoToMyPC, Chrome Remote Desktop, UPnP/SSDP, NetBIOS Name Service, SMB v1/v2 and Windows File Sharing; the FortiOS default services REXEC, RLOGIN, RSH, DCE-RPC, ONC-RPC and the other 7.x defaults, which were read as unknown services and slipped past the port checks; the SRX AppSecure spellings of GoToMyPC and Elasticsearch; and custom SRX applications named after a remote access tool (e.g. `AnyDesk-Custom`) now keep their name, as FortiGate services already did, so the service name check sees them.
- New examples: `corner_cases_1000.csv` with its FortiGate and SRX versions (1,000 rules that trigger 42 of the 43 finding types and their corner cases), `fortigate_demo_30rules.conf` and `srx_demo_30rules.set` (the 30 rule demo on the other two vendors, with hit counters) and `objects_corner_*.csv` (address objects and groups).

### Changed
- plain_dns_to_unrestricted_destination and plain_dns_to_known_resolver now also fire for the DNS application (`dns`, `dns-base`), not only for port 53: the same traffic gets the same finding whether the rule is written the App-ID way or the port way, on every vendor.
- Gemini request, no IP address ever leaves the machine: rule names are masked too now (`Allow-10.1.1.1` becomes `Allow-IP-MASKED-1`), as are IPv6 addresses and IPv4 written with `_` or `-` between the octets (`Host_10_1_1_1`, `net-192-168-10-0`), everywhere text is sent (findings, tags, trend). The same address gets the same placeholder in every form. Right before the request leaves, it's scanned again with the same patterns, and if an address were still in it, nothing is sent. When the model answers about a masked rule name, the answer is matched back to the real rule locally.
- Checks whose meaning depends on the platform now adapt to the source vendor (PAN-OS results are unchanged):
  - port_based_rule_missing_app_id: on FortiGate it isn't reported when an application control profile is applied, and the text recommends application control; on SRX it recommends AppSecure.
  - missing_explicit_intrazone_internet_deny: only where intrazone traffic is really allowed without a rule (every zone on PAN-OS, FortiOS zones with `intrazone allow`, and on SRX only with `default-policy permit-all`).
  - rule_usage_unused / rule_usage_partially_used: these are Panorama's own verdicts and are never derived from hit counts on other vendors, otherwise the same fact would be reported twice next to zero_hit_count.
  - Finding texts say "application" instead of "App-ID" for FortiGate, SRX and Tufin rules.
- The vendor is recognized from the file content, so a configuration passed to -InputCsv, which is what happens through the interactive setup, is analyzed as a configuration instead of failing as a broken CSV.
- A hit counter or rule usage file given as the file to analyze (FortiGate monitor API JSON, SRX hit-count output, PAN-OS rule usage CSV) is now recognized and explained: the interactive setup keeps it as the hit counter file and asks for the configuration, while the command line stops and shows the right usage. A file in no known format is refused instead of being read as a PAN-OS CSV (a `.csv` file is still read as one, as before). Quotes around a path pasted in the interactive setup are accepted.
- The interactive setup now follows the input type: address object/group files and a rule usage file for a PAN-OS CSV, hit counter file and application name map for FortiGate and SRX. The review list is rebuilt when you change the input file.
- The report title and the Gemini system prompt follow the source vendor, so AI remediation advice talks about FortiOS or Junos features rather than PAN-OS ones.
- The banner tagline now reads "Firewall Rule Analyzer".
- After the AI step of a live run, that run's findings CSV is rewritten with the Suggested Fix and MITRE ATT&CK columns (before, only the HTML and the JSON had them). Offline CSVs are unchanged.
- The question about including rule Tags in the Gemini prompt is skipped when no rule has Tags.
- The AI step is now a single function shared by live runs and saved report analysis; nothing changes in a live run.

### Fixed
- Shadowing, duplicate and anomaly checks compared rules of different FortiGate VDOMs or SRX logical systems with each other (the same policy in two VDOMs was reported as a duplicate), and generalization_anomaly could pair a rule with a broader rule of another VDOM. Rules are now compared only within the same VDOM, logical system or device; PAN-OS output is unchanged.
- Address objects and groups, checked across the three vendors with `examples/objects_corner_*.csv` and `rules_5000_with_objects.csv`:
  - A FortiGate `interface-subnet` object without a subnet line resolved to 0.0.0.0/0 (any). It now takes the interface's subnet, or stays opaque.
  - IPv6 addresses and bare numbers were read as IPv4 (`2001:db8::1` as 0.0.0.1, which is inside 0.0.0.0/0, and an object named `10` as 0.0.0.10). Only dotted IPv4 counts as an address now; the rest stays opaque. SRX IPv6 addresses get their own type, as on FortiGate.
  - A negated object or group in a PAN-OS CSV (`[Negate] GUEST-G`) stayed one opaque token. It's resolved now, as FortiGate and SRX already did.
  - An empty group resolved to an empty field, which reads as any. It's one opaque token now.
  - negated_rfc1918_effectively_public fired when only part of the private space was negated (`[Negate] 10.60.0.0/16` isn't "any public"), and all_rfc1918_effectively_private fired on 0.0.0.0/0. Both now require exactly what their text says; those rules still count as broad for the other checks.
- Hit counts above 2,147,483,647 (common on busy edge rules) no longer stop the run: zero_hit_count and stale_last_hit read the counter as a 64 bit value.

## [2.1] - 2026-09-23
### Added
- generalization_anomaly: an earlier, narrower rule fully covered by a later, broader rule using a different action (the Al-Shaer/Hamed Generalization anomaly, the same term Palo Alto Strata Cloud Manager uses in its Policy Analyzer). The narrow rule still fires today as a deliberate looking exception ahead of the broad one; the risk is fragility, not brokenness. Removing that rule during cleanup, on the wrong assumption the broad rule already covers it, or reordering the two, silently changes the effective behavior for its traffic, with nothing in the firewall itself flagging the change. Low severity: a warning to confirm intent, not a confirmed misconfiguration. Detected through a bounded backward scan, run only when the current rule looks broad enough to plausibly generalize something (wildcard zone, or source/destination address left as any), so the added cost scales with how many such broad rules exist, not with the square of the ruleset size.
- correlation_anomaly: two rules with different actions whose match criteria partially overlap without either one containing the other (the other half of the same Al-Shaer/Hamed pair, called Correlations in Strata Cloud Manager). Neither rule is dead policy and neither is a deliberate exception; for traffic caught in the overlap, the effective action depends only on which rule sits first in the rulebase, something neither rule states on its own. Low severity, reported once per rule.
- exposed_amplification_prone_service: allow rule reachable from the internet on a UDP service known to be abused for reflection and amplification DDoS (NTP, SSDP/UPnP, mDNS, NetBIOS Name Service, Memcached, Chargen, QOTD, full list in README), matched by App-ID or by UDP port through a port parser limited to UDP (the same port number over TCP does not carry this risk, since it needs a spoofable, connectionless response). Framed as a risk to third parties, not only to this network: the attacker spoofs a victim's source address, and a server answering this from the open internet becomes the reflector, sending its, often much larger, response to the victim instead of back to the attacker. High severity. Extensible through the two new optional keys in `-RiskyTaxonomyPath`, `amplificationPronePorts` and `amplificationProneApplications`.
- generic_rule_name: rule named after a generic template rather than what it actually controls (Rule 5, New Rule, Policy #12, a bare number, and similar, matched in both English and Italian). This kind of name only works if the reader also knows the rule order; on its own it says nothing about the traffic. Low severity.
- compliance_tag_without_critical_zone: allow rule tagged with a compliance or critical scope keyword (pci, swift, cde, cscf, hipaa, phi, sox, ffiec, core banking, atm, hsm) whose source and destination zone are both outside the configured `-CriticalZones` set. Either the tag no longer matches what the rule actually touches, or the critical zone list is missing something the organization already considers in scope. Skipped when either zone is any, since any already includes the critical zone among everything else it matches. Medium severity.
- no_explicit_deny_log_rule: ruleset wide check for a broad deny or drop rule (any zone, any address, any application, any service) with logging enabled. Without one, whether traffic caught by the implicit default deny is actually logged depends on a device setting this export cannot see. Low severity, a defense in depth recommendation rather than a confirmed gap; skipped entirely when the export never shows logging information anywhere, same gate as 'no_logging_enabled'.

### Changed
- RiskyTaxonomyPath json schema extended with two more optional top level keys, 'amplificationPronePorts' and 'amplificationProneApplications', merged the same additive way as the existing 'riskyPorts'/'riskyApplications' (a custom entry sharing a key with a built in one only overrides that entry's label).

## [2.0] - 2026-09-11
### Added
- The Findings table (report and CSV export) and the Internet Exposure Inventory now show the resolved IP/CIDR alongside a raw address-object or group name when -AddressObjectsCsv/-AddressGroupsCsv resolution actually changed something (e.g. Network1 (10.0.0.0/8)), so a reader doesn't need to cross-reference the objects file separately to know what a name means. Left as just the name when resolution didn't apply.
- RiskyTaxonomyPath: an optional JSON file extending the built-in risky-port/application tables with environment-specific entries.
- OutJson: a structured JSON Lines export of the findings (one finding per line, each an independently parseable JSON object with metadata repeated on every line) meant for a SIEM or other automated consumer. Chosen over a single nested JSON document specifically because log-oriented ingestion (Splunk and similar) indexes JSON Lines automatically, with fields like severity/rule_name/type immediately searchable, no unpacking required. Written once after the deterministic report and again (overwriting) after the optional Gemini step if that ran, so it reflects Suggested Fix/MITRE tags when available.
- Trend narrative on -CompareTo: when a comparison against a previous report has actual changes, and the optional Gemini step runs, you're asked separately whether to also get a short AI narrative about the trend (what got fixed, what's new, whether it reads as real progress or churn), shown under the New/Resolved/Still-present counts.
- "-Model" now appears in the guided interactive setup and in the review
  and edit console, not just on the command line. Prompt shows the
  current default (gemini 3.7 flash) and accepts a blank answer to keep
  it. Toggling AI analysis back on inside the console also brings the
  Model row back with it.
### Fixed
- Zone="any" no longer implies internet-touching on a ruleset where no zone actually named as an internet zone (via -InternetZones) exists anywhere at all - a purely internal firewall, with no Untrust/external- equivalent interface on the device. Computed once per ruleset (does at least one real zone in use anywhere match a configured internet zone name); when the answer is no, "any" matching "every zone the firewall knows about" can no longer include the internet, because none of those zones IS the internet. A concrete public/negated address is unaffected either way, since that evidence is independent of zone naming. Where a real internet zone does exist somewhere in the ruleset, behavior is unchanged.
- Address-object resolution silently failed for a common variant type spelling: the code matched only the literal string "ip-netmask", so an export using "IP Netmask" never resolved at all, leaving the raw object name as an opaque token for every downstream check that depends on knowing whether an address is public or private. Object types are now normalized (lowercased, spaces collapsed to hyphens) before comparing.
- A large ruleset needing multiple Gemini batches produced a visibly repetitive AI section: each batch's prompt didn't know it was only seeing a slice of the findings, so every batch tended to write a "complete" executive summary describing the same dominant, ruleset-wide issues (e.g. one broad any/any rule whose shadowed-rule findings spread across several batches), and those near-duplicate summaries were then simply concatenated. Fixed on both ends: batches are now told when they're one of several and asked to describe only what's actually in front of them, and the final report uses just the summary from the batch with the most Critical/High findings (noting how many batches ran) rather than stitching every batch's summary together. The remediation list is also deduplicated by shared rule-name tokens across batches, so the same headline rule recommended three or four times in slightly different words collapses to one entry.
- Gemini calls stopped giving up on the very first client side timeout.
  HttpClient's own default timeout (100 seconds) could expire before a
  larger batch got an answer, surfacing as a raw TaskCanceledException
  ("A task was canceled") straight
  out of GetAwaiter().GetResult(). That path used to return immediately
  instead of going through the retry logic already built for transient
  HTTP errors (429/500/502/503/504), so "attempt 1/3" never actually
  reached attempt 2 or 3. The request timeout is now explicit (180
  seconds) and a client side timeout retries with the same exponential
  backoff as those HTTP errors.

## [1.8] - 2026-09-07
### Added
- Port 80 (HTTP) added to the risky-port list, marked cleartext like FTP/Telnet/etc. Previously absent entirely, not just excluded from the cleartext subset.
- MITRE ATT&CK tagging: when the optional Gemini step runs, findings that clearly correspond to a well-known technique get tagged with its ID, name, and tactic in a new column, shown only when at least one finding has been tagged. The model is instructed to skip a finding rather than force a speculative or overly generic tag.
- Interactive setup now ends with a review-and-edit loop once the guided question sequence completes: every parameter is listed with its current value, and typing a number or a parameter name (by either, case-insensitive) lets you change just that one setting and come back to the list, instead of having to restart the whole wizard to fix one answer. Press Enter with no changes to proceed.
- Large rulesets that produce enough findings to risk exceeding Gemini's free-tier input-token quota are now automatically split into multiple smaller batches, sent one after another, with results merged afterward. A console note explains when this kicks in. Batches are spaced more than 60 seconds apart, since the quota that matters is cumulative per minute, not per request. Sending several comfortably-sized batches only a few seconds apart can still trip the same quota this batching exists to avoid.
### Changed
- The Suggested Fix column now only appears when the optional Gemini step actually runs.
### Fixed
- Direction classification (Test-SideIsInternet) no longer treats a rule as internet-facing purely because its zone is "any" if the address field on that same side is exclusively a specific, plain private IP/CIDR - PAN-OS matches zone and address together on a rule, not either alone.
- The same zone="any" issue fixed earlier for direction classification (Test-SideIsInternet) was also present, independently, in three places that compute their own "which dimensions are open" list without going through that function: unrestricted_access_to_critical_zone, unrestricted_egress_from_critical_zone, and internet_exposed_any_field. All three were counting a zone field as unrestricted just because it said "any", even when the address field on that same side was a specific, bounded subnet that would have narrowed the actual matched traffic considerably. Fixed the same way: a zone="any" signal only counts as open when the address on that side doesn't already narrow it down.

## [1.7] - 2026-08-31
### Added
- Suggested Fix column on the Algorithmic-based Findings table, shown whenever at least one finding has one. Filled in automatically (no AI needed) for finding types with an obvious, context-free next step: disabled_rule_present / rule_usage_unused / stale_last_hit (candidates for removal, confirm with the rule owner), duplicate_rule / shadowed_rule (remove, covered by an earlier rule), and temporary_tag_but_broad_rule / temporary_tag_still_present (confirm still needed, remove tag or rule if not). When the optional Gemini step runs, the same prompt also asks for a plausible App-ID guess specifically for any_any_any_allow, outbound_defined_dest_any_app, and port_based_rule_missing_app_id findings, based on the rule's name, its Tags (if included), and any port already visible in the finding text. AI guesses are clearly prefixed "AI guess (verify):" and are never applied automatically; a finding is left without one if there's no real hint in the name/ tags/port to go on rather than guessing something generic. Applying a suggestion (deterministic or AI) rebuilds the report from the already-computed findings, no re-detection involved.
- Table columns on the Findings and Inventory tables can now be dragged to a new position by their header label (distinct from the resize handle on the right edge of each header). Moving a column reorders it consistently across the header, the filter row, and every data row, so filtering keeps working correctly regardless of column order. Works with both mouse and touch.
### Fixed
- internet_exposed_any_field no longer counts Application left as "any" as an open dimension when Service is pinned to a specific port (e.g. tcp/8080). That combination is a port-based rule, not a wide-open one, and was already its own finding (port_based_rule_missing_app_id); counting it here too overstated how open the rule actually was. Application still counts normally when Service is also effectively any.
- outbound_defined_dest_any_app had the same issue as the fix above, and is fixed the same way: Application left as "any" only counts as unrestricted when Service is also effectively any, not when Service is pinned to a specific port.
- The same Application/Service issue as the two fixes above was also present in five more places, found by systematically re-checking every spot that looks at whether Application is "any": unrestricted_access_to_critical_zone, unrestricted_egress_from_critical_zone, temporary_tag_but_broad_rule (which was also missing a Service check entirely, not just misapplying one), broad_internal_exposure (which used a plain null check on Service instead of the shared effectively-any helper, missing the application-default-with-no-app edge case too), and missing_explicit_intrazone_internet_deny (the mirror situation: a Deny rule with Application=any but Service pinned to one port doesn't actually block all traffic between the zone and itself, so it shouldn't count as satisfying the "explicit deny" requirement either). All five fixed the same way, reusing the shared Service-effectively-any check.
- Direction classification (Test-SideIsInternet, which most findings key off of) no longer treats a rule as internet-facing purely because its zone is "any" if the address field on that same side is exclusively a specific, plain private IP/CIDR. PAN-OS matches zone and address together on a rule, not either alone, so a rule scoped to zone="any" but a concrete private host (e.g. 10.5.5.10/32) can never actually be reached from internet, no matter how broad the zone field looks by itself. A specifically-named internet zone (e.g. Untrust) is unaffected by this and still counts as before; so does any address that's public, negated, a range, or an unresolved object name, only an unambiguous, exclusively-private plain IP/CIDR overrides the zone="any" signal.
- inbound_risky_application / outbound_risky_application / internal_risky_application now also check the Service field for a risky application name, not just Application. Real, especially older, rulebases sometimes use a custom-named Service object literally named after the protocol instead of, or alongside, App-ID (e.g. a Service named "smtp") - a pre-App-ID naming convention that was previously invisible to these checks entirely, since Service was only ever scanned for port numbers. Also matches a name with a port or other suffix appended to it (e.g. "smtp-25", "SMTP_Relay_25"), by checking each sub-token split the same way rule names are tokenized elsewhere in this file, not just an exact whole-field match.

## [1.6] - 2026-08-31
### Added
- outbound_icmp_to_unrestricted_destination: outbound rule permits ICMP-family traffic (App-ID ping, icmp, ipv6-icmp, or traceroute, or a Service object literally named icmp as a fallback) to an unrestricted destination (any, or effectively any via the RFC1918 idiom). ICMP is often overlooked by inspection compared to TCP/UDP traffic; data can be encoded in echo/payload fields to exfiltrate data or maintain a covert C2 channel. Not flagged when the destination is scoped to specific, known hosts.

## [1.2] - 2026-08-22
### Added
- rule_name_action_mismatch: flags a rule whose name suggests it denies/blocks traffic (contains a token like "deny", "block", "drop") but is actually configured to allow it, or vice versa (a name suggesting "allow"/"permit" on a rule that's actually deny/drop). A rule renamed or toggled without the other catching up is easy to miss on a quick read and easy to trust incorrectly. Matched by exact token, not substring; rules whose name contains both a deny-style and an allow-style token are skipped as ambiguous rather than guessed at.
### Fixed
- The double-quote-wrap CSV repair now applies iteratively instead of once. The repair now loops until the line no longer matches the wrapped signature, capped at 5 passes, with a second check (a minimum count of "" pairs in the line) to avoid misfiring on a normal, unwrapped CSV that happens to start with a short quoted field (this could be fired depending on witch device the export is done from).
